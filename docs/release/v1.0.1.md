# pretty-lang v1.0.1 — unlimited width and a linear fit test

**A patch for two engine bugs.** `render(usize::MAX)` broke every group instead of laying everything flat, and rendering was quadratic on documents with a lot of zero-width content. Both are fixed. There is no public API change; upgrading is a `cargo update`.

**Layouts are unchanged** at every width up to `isize::MAX`: the new fit test makes the same decisions as the old one, checked against a line-for-line port of the `1.0.0` renderer on random documents. The only layouts that change are those at widths above `isize::MAX`, which were wrong.

## M64: `render(usize::MAX)` broke every group

`1.0.0` converted the target width with `width as isize`. `usize::MAX` became `-1`, and every width above `isize::MAX` became negative. With a negative width nothing fits, so every group took its broken form: the "unlimited width" layout was the narrowest layout there is.

```rust
let doc = Doc::text("a").append(Doc::line()).append(Doc::text("b")).group();
doc.render(usize::MAX)   // 1.0.0: "a\nb"    1.0.1: "a b"
```

The width is now clamped to `isize::MAX` (`isize::try_from(width)`, else `isize::MAX`). Every width at or above `isize::MAX` means "unlimited" and behaves exactly like `isize::MAX`, so `usize::MAX` is the natural way to ask for the widest layout. A hardline still forces its groups to break at any width.

**The crate's own benchmarks hit this.** `benches/bench.rs` used `usize::MAX` as its "fits on one line" width, so its `render_flat` numbers, and the README table built from them, timed the fully broken layout. The flat benches now assert that their output is one line before they measure it. Corrected numbers are below.

## M65 (patch part): rendering was quadratic on zero-width content

At each group the renderer asks: *does the group, laid out flat, plus whatever follows it up to the next line break, fit in the columns left on this line?* `1.0.0` answered by scanning forward until the width ran out or a line break was reached. For ordinary text that scan is bounded by the width. But zero-width content (`nil`, empty `text`, flat `softline`s, nested groups) never uses up the width, so a group followed by a lot of it rescanned all of it, and so did the next group, and the next. Rendering 100,000 `softline` groups took about 50 seconds. The scan also allocated a fresh `Vec` for every group.

The fit test is now O(1), with no scan and no allocation:

- Every node records two widths when it is built, in O(1) from its children: its width laid out flat (a hardline counts as infinitely wide, which is how it forces its groups to break), and its width in broken form up to the first line break it owns.
- Every entry on the render work stack records how many columns it and everything queued after it use before the current line ends. Pushing an entry computes this in O(1) from the entry below.
- A group fits exactly when its flat width plus that total is within the columns left. That is one addition and one comparison.

Rendering is now one pass, linear in the size of the document, at every width. The render path allocates only its work stack (plus the output `String` for `render`).

### Why the decisions are the same

The old scan's answer depends only on the total width of what it would have scanned before stopping, and on whether it stopped at a line break or at a flat hardline. Widths are never negative, so "the running width never exceeded the space left" is the same as "the total up to the stop is within the space left". Those totals compose: a sequence's width before its first line break is the first part's width if that part contains a break, and otherwise the first part's flat width plus the second part's. Infinite width (a flat hardline) never fits, which matches the scan's immediate failure. The summaries compute this total directly instead of walking to it.

`tests/equivalence.rs` checks the claim, not just the argument. It holds a line-for-line port of the `1.0.0` renderer over an independent mirror tree (with the M64 clamp, the one intended change) and compares the output byte for byte on 2 × 4,096 random documents per run. The documents are weighted towards zero-width content, include shared subtrees and multi-byte text, and are rendered at random widths and at 0, 1, `isize::MAX`, `isize::MAX + 1`, and `usize::MAX`, both bare and wrapped in a group. Four deliberate one-line bugs in the new code (`<=` to `<`, a dropped prefix width in sequence composition, a broken-mode stop treated as pass-through, a large finite hardline width) are each caught by it.

## Widths are counted in `char`s (documented, not changed)

Every width in the crate is `chars().count()`: Unicode scalar values, not bytes and not terminal display cells. That applies to `text`, to the target `width`, and to indentation. A CJK character or an emoji (two cells in a terminal) counts as one; a combining mark (zero cells) counts as one; a tab counts as one. The rustdoc, `docs/API.md`, and the README now say so exactly, and unit tests pin each case.

Changing to display width would change the layout existing documents produce, so it cannot ship in `1.x` as a default. It is recorded in `dev/ROADMAP.md`: an opt-in caller-supplied-width constructor is additive (1.1), and display width by default is 2.0. The same section records `Send` documents (`Arc`, 2.0) and the `align`, `if_break`, and `fill` combinators (additive, 1.1).

## Performance

All numbers are from one Windows x86_64 machine, Rust 1.95 stable, release build with fat LTO. The `1.0.0` side was built from the `v1.0.0` sources with the same code.

### Pathological shapes (render at width 80)

`1.0.0` at 10k is a Criterion mean. At 100k it is a single timed render (Criterion would need several minutes per shape), and at 1M one `softline_groups` render was started and killed after 900 seconds without finishing. `1.0.1` numbers are Criterion means (10 samples).

| Shape | Items | 1.0.0 | 1.0.1 |
|---|---:|---:|---:|
| `softline_groups` (`n` × `group(softline)`) | 10,000 | 213.50 ms | 130.28 µs |
| | 100,000 | 50.027 s (one run) | 7.1673 ms |
| | 1,000,000 | did not finish in 900 s | 119.02 ms |
| `nil_groups` (`group(n × group(nil))`) | 10,000 | 215.34 ms | 135.21 µs |
| | 100,000 | 46.049 s (one run) | 3.9878 ms |
| | 1,000,000 | not run | 114.62 ms |
| `empty_text_groups` (`group(n × group(text("")))`) | 10,000 | 230.78 ms | 147.94 µs |
| | 100,000 | 73.037 s (one run) | 7.3063 ms |
| | 1,000,000 | not run | 137.52 ms |

The `1.0.1` times grow faster than 10× per 10× items between 10k and 1M. That is memory, not the algorithm: a document of the same shape with no groups at all, which never runs the fit test, scales the same way (one-shot best: 112.4 µs / 5.700 ms / 120.3 ms at 10k / 100k / 1M). At 1M items the document is roughly 3M nodes and ~170 MB, so the walk is bound by cache misses.

The real flat layout was the slow case in `1.0.0`: at an unlimited width the scan never runs out of width, so every nested group rescanned to the end of the document (4.6× slower than the broken layout on the deepest JSON tree). In `1.0.1` flat and broken cost about the same, and both are faster than `1.0.0`'s broken path because no group scans at all. `build_and_render` is within noise of `1.0.0`: building pays for the larger nodes and the summaries, rendering gets that back. Building alone was not measured separately.

The machine was shared with other builds while these ran, so treat differences under about 15% as noise.

## Memory

Each node now carries its width summary, so a `Doc` node grows from 32 to 40 bytes (48 to 56 bytes per `Rc` allocation on 64-bit targets). Building a document costs one extra addition or comparison per combinator.

## Breaking changes

**None.** The public surface is identical to `1.0.0`. The layout at a width above `isize::MAX` changes, from the wrong all-broken layout to the unlimited layout; every other layout is identical.
